Problema & Solución

Problema

Equipos industriales fallan sin avisar, causando paradas costosas. El mantenimiento reactivo es manual, tardío y sin visibilidad operacional en tiempo real.

Solución

Sistema distribuido que monitorea vibración de sensores 24/7, detecta patrones de falla automáticamente, alerta en <1s y ejecuta acciones correctivas.

Valor clave: Combina ingesta masiva (Kafka) con decisión humana (RabbitMQ + Web UI) en un flujo de extremo a extremo.

Arquitectura del Sistema

3 capas · 11 servicios Docker · Flujo unidireccional de extremo a extremo

1. Capa de Ingesta y Análisis Apache Kafka KRaft

  • sensor_producer — Simula 10 sensores (A–J), publica en Kafka cada 500ms
  • alert_detector — Ventana deslizante de 3 lecturas, detecta CRITICAL / WARNING
  • plant_monitor_backend — WebSocket :8081, telemetría en vivo de toda la planta
▼

2. Capa Transaccional RabbitMQ + Workers

  • alert_router — Bridge Kafka → RabbitMQ, enriquece alertas con opciones contextuales
  • operator_console_backend — WebSocket :8082, alertas al operador humano
  • action_dispatcher — REST API POST /decide (puerto 3001)
  • notification_service — Telegram + panel móvil (puerto 3003)
▼

3. Capa de Ejecución RabbitMQ Workers

  • actuator_worker — Apagados críticos (critical_actions_queue)
  • maintenance_worker — Mantenimiento inmediato y diferido (delayed exchange)
Infraestructura: Kafka RabbitMQ orquestados con Docker Compose en red bridge personalizada (iot-network)

Reglas de Detección de Fallas

CRÍTICA — Vibración instantánea > 90 mm/s
Alerta inmediata, requiere acción urgente del operador
WARNING — Ventana deslizante de 3 lecturas consecutivas con promedio > 75 mm/s
Patrón de deterioro, se puede programar mantenimiento
Técnica: Ventana deslizante (sliding window) en memoria con tamaño 3 — evita falsos positivos por picos aislados.

Nota: Los sensores generan valores normales (42–74 mm/s) con ráfagas programadas de warning (76–78 mm/s × 3) y una crítica (>90 mm/s) periódicamente.

4 Acciones del Operador

AcciónTipo AlertaCola RabbitMQEfecto en Simulación
APAGADO_INMEDIATO CRÍTICA critical_actions_queue Sensor → SHUTDOWN (sin lecturas)
IGNORAR_10_MINUTOS CRÍTICA delayed_exchange (10 min) Sensor → COOLDOWN, se reactiva tras 10 min
PROGRAMAR_MANTENIMIENTO_AHORA WARNING maintenance_queue Sensor → MAINTENANCE (~45s sin lecturas)
RECONOCER_Y_ESPERAR_24H WARNING delayed_exchange (24h = 15s simulado) Sensor → COOLDOWN, se reactiva tras 24h
Human-in-the-Loop: El sistema no decide solo. El operador recibe la alerta por WebSocket + Telegram y elige la acción desde el dashboard o el panel móvil.

Ciclo de Vida de los Sensores

ACTIVE → SHUTDOWN ← COOLDOWN ← MAINTENANCE

ACTIVE

Estado normal. El sensor produce lecturas cada 500ms.

SHUTDOWN

Apagado crítico. No produce lecturas.

COOLDOWN

En espera temporizada. Se reactiva automáticamente.

MAINTENANCE

En mantenimiento (~45s). Se reactiva al terminar.

El sensor_producer expone un endpoint POST /control para que las decisiones del operador afecten la simulación en tiempo real.

Decisiones de Diseño Destacables

Doble WebSocket

Puerto 8081 para telemetría en vivo, 8082 para alertas del operador. Soluciona el solapamiento de puertos del enunciado original.

Bridge Kafka → RabbitMQ

alert_router traduce mensajes entre brokers heterogéneos, enriqueciendo alertas con opciones contextuales.

Anti-saturación Telegram

Cola con deduplicación, intervalo mínimo entre envíos y long-polling single-thread para evitar error "Conflict: terminated by other getUpdates".

Delay simulado 15s

La opción "Esperar 24h" se simula con 15 segundos para demostración en vivo sin esperar horas reales.

Particionamiento por clave

Eventos de un mismo sensor caen en la misma partición de Kafka, garantizando orden secuencial.

Puerto externo 3001

El action_dispatcher escucha internamente en 3000 pero se mapea como 3001 para evitar colisiones.

Patrones de Integración

Particionamiento por clave (Kafka)

Todos los eventos de un sensor caen en la misma partición, garantizando orden secuencial estricto.

Ventana deslizante (Sliding Window)

En memoria, tamaño 3. Evita falsos positivos por picos aislados.

Fanout Exchange (RabbitMQ)

Distribución masiva a múltiples consumidores (WebSocket, Telegram, panel móvil).

Delayed Message Exchange

Plugin x-delayed-message para tareas programadas (ignorar 10min, esperar 24h).

Human-in-the-Loop

Operador humano recibe alerta y decide la acción correctiva. El sistema no actúa sin supervisión.

Conexión resiliente

connectWithRetry en todos los servicios con reintentos hasta que brokers estén listos.

Conceptos Clave para la Exposición

1. Kafka ≠ RabbitMQ

Kafka = ingesta masiva, ordenado por partición, alto throughput. RabbitMQ = enrutamiento inteligente, colas, delayed messages. Cada uno en su rol.

2. Bridge de interoperabilidad

alert_router traduce mensajes entre dos sistemas de mensajería distintos — patrón fundamental en sistemas distribuidos heterogéneos.

3. Human-in-the-Loop

El operador humano es parte del flujo. No es solo supervisión: es un nodo activo que toma decisiones críticas.

4. Tolerancia a fallos

Reconexión automática, sensores con ciclo de vida, colas persistentes, deduplicación de notificaciones.
